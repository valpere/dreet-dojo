# DreetDojo — Requirements

Вимоги до MVP 1.0. Сценарії: [use-cases.md](use-cases.md). Архітектура: [architecture.md](architecture.md).
Детальний дизайн: [hld.md](hld.md).

## Призначення

Це локальний контейнеризований тренажер, щоб відновлювати й підтримувати навичку активного програмування (*coding fluency*). Він поєднує три речі:
- інтервальне повторення (SRS);
- таймовані мікро-вправи, які перевіряє реальний компілятор і тести;
- «стерильний» редактор без автодоповнення й AI.

Базова мова MVP — Go. Архітектура закладає розширення на інші мови та альтернативні клієнти.

## 1. Функціональні вимоги (FR)

### Колоди та формати вправ

- **FR-01.** Система завантажує декларативні колоди з файлової системи (`meta.yaml`, `prompt.md`, `go.mod`, `kata.go`, `kata_test.go`, `solution.go`). Нові або змінені картки підхоплюються без перезбирання образу.
- **FR-02.** Поле `format` підтримує 5 типів вправ:
  - `cloze`: заповнити пропуск;
  - `spec`: від ТЗ до коду;
  - `progressive`: ланцюжок етапів через `prereq`;
  - `bugfix`: знайти й виправити баг;
  - `skeleton`: оголосити контракти й типи.
- **FR-03.** Команда `dreet validate` гарантує інваріант кожної картки:
  - стаб не проходить тести;
  - еталон проходить тести під `-race` без гонок і попереджень;
  - граф `prereq` коректний: посилання ведуть на наявні картки, циклів немає.

### Стерильний редактор і UX одного вікна

- **FR-04.** Веб-інтерфейс збирає в одному вікні редактор, панель умови з таймером і підказками, вивід тестів і переглядач diff. Перемикатися в термінал не потрібно.
- **FR-05.** Редактор працює в «стерильному режимі»:
  - **дозволено:** підсвітку синтаксису, автовідступи, підсвітку парних дужок, інлайн-маркери помилок від раннера;
  - **заборонено:** автодоповнення, LSP, сніпети, AI-підказки, автозакриття дужок.
- **FR-06.** Основний цикл керується з клавіатури: `Ctrl+S` перевіряє рішення, `Alt+H` дає підказку, `Alt+D` показує diff, `Alt+N` видає наступну картку.
- **FR-07.** Еталон (`solution.go`) недоступний ні через API, ні з пісочниці, доки поточна спроба не завершиться (`pass` або `giveup`).

### Виконання коду та діагностика

- **FR-08.** Go-вправу перевіряє реальний компілятор командою `go test -race -json -count=1 -timeout=5s ./...` в ізольованій тимчасовій директорії, без доступу до мережі.
- **FR-09.** Ядро розрізняє 4 статуси перевірки (`pass`, `compile_error`, `test_fail`, `timeout`). Воно повертає масив структурованих діагностик `{file, line, col, severity, message}`, щоб показати їх у рядках редактора.
- **FR-10.** Коли спрацьовує таймаут, система примусово знищує процес разом із групою дочірніх процесів (PGID). Завислих або зомбі-процесів не лишається.

### Інтервальне повторення (SRS) та телеметрія

- **FR-11.** Оцінка 1–4 виводиться автоматично з об'єктивних метрик: `elapsed_sec` відносно `target_sec`, `compile_errors`, `test_fails`, `hints_used` і статусу спроби. Користувач оцінку не обирає.
- **FR-12.** Інтервали розраховує адаптований SM-2:
  - перші інтервали 1 → 3 дні;
  - `EF` у межах [1.3, 3.0], стартове значення 2.5;
  - максимальний інтервал 60 днів;
  - jitter ±5% для інтервалів від 4 днів.
- **FR-13.** Планувальник враховує залежності `prereq`: нова картка не видається, доки батьківська не має `reps >= 1`. Діє денний ліміт нових карток: конфігурований, за замовчуванням 3.
- **FR-14.** Статистика за 30 днів:
  - черга на сьогодні;
  - скільки карток пройдено сьогодні;
  - частка спроб без жодної помилки компіляції;
  - топ слабких тегів за середньою оцінкою.
- **FR-15.** Активна спроба відновлюється після перезавантаження сторінки. Таймер і лічильники при цьому не скидаються, а UI отримує поточний код із пісочниці.

## 2. Нефункціональні вимоги (NFR)

| Категорія | ID | Вимога та вимірюваний критерій |
| :---- | :---- | :---- |
| Швидкодія | **NFR-01** | Медіанний час `POST /api/attempt/run` для типової Go-вправи з `-race` — **≤ 500 мс**. Це досягається прогрітим `GOCACHE` і tmpfs для `/work` та `/tmp`. |
| Швидкодія | **NFR-02** | Холодний старт контейнера до готовності HTTP — **≤ 2 с**. JS-бандл фронтенду — **≤ 500 КБ** у gzip. |
| Безпека та ізоляція | **NFR-03** | Порт публікується виключно на `127.0.0.1:8787` хоста. Контейнер працює від непривілейованого користувача `dreet` (UID 10001) з такими налаштуваннями: `read_only: true`, `cap_drop: ALL`, `no-new-privileges: true`, `mem_limit: 1g`, `pids_limit: 128`, `cpus: 2.0`. |
| Безпека та ізоляція | **NFR-04** | `kata_test.go` і каталог колод (`/app/decks`) доступні лише для читання. Користувач може писати тільки в цільовий файл вправи всередині `/work/<session_id>/`, і цей запис захищено від path traversal. |
| Надійність даних | **NFR-05** | SQLite працює в режимі WAL з `foreign_keys=ON` і `busy_timeout=5000`. Стан картки й запис спроби фіксуються в одній транзакції. Історія та розклад переживають перезапуск контейнера. |
| Розширюваність | **NFR-06** | Нова мова (Python, Rust, TypeScript) не потребує змін у `srs`, `sandbox`, `api`, `session` чи схемі БД. Досить нової реалізації `Runner` і відповідного runtime-образу. |
| Розширюваність | **NFR-07** | Бізнес-логіка не прив'язана до HTTP. Поверх тих самих сервісів можна додати stdio JSON-RPC транспорт для плагінів редакторів (VS Code, Lite XL) без дублювання логіки. |
| Підтримуваність | **NFR-08** | Бінарник `dreet` компілюється з `CGO_ENABLED=0`, SQLite підключено через pure-Go `modernc.org/sqlite`. HTTP працює на stdlib `net/http`, без веб-фреймворків. Кожна стороння залежність має письмове обґрунтування, чому stdlib не вистачає (див. architecture.md). |

## 3. Обмеження

- Go **1.26+** для ядра і для `go.mod` карток.
- Runtime-образ на Debian/glibc (`golang:1.26-bookworm` або новіший Debian-тег). **Alpine заборонено**, бо `-race` потребує glibc і CGO під час прогону тестів.
- Фронтенд: TypeScript, Vite і CodeMirror 6. Важких UI-фреймворків (React, Angular, MUI) немає. Бандл вшивається в бінарник через `//go:embed`.
- Вправи MVP спираються лише на стандартну бібліотеку. Під час перевірки мережа не потрібна, а `GOPROXY=off`.

## 4. Межі MVP (Out of Scope для v1.0)

- Автентифікація, багатокористувацький режим, хмарна синхронізація.
- Генерація вправ через LLM у веб-інтерфейсі. Її винесено в офлайн-процес поза ядром.
- Зовнішні Go-модулі з мережі під час виконання вправ.
- Нативні плагіни VS Code / Lite XL і stdio JSON-RPC транспорт. Архітектура їх передбачає, реалізація буде після валідації MVP.
- Інші мови, крім Go. Передбачено через `Runner`.
- FSRS замість SM-2. Планувальник ізольовано, тож заміна можлива пізніше.

## 5. Критерії приймання MVP (Acceptance Criteria)

1. **AC-1.** `docker compose up --build` піднімає контейнер на `127.0.0.1:8787` з усіма налаштуваннями NFR-03, а `GET /api/health` повертає `200`.
2. **AC-2.** `dreet validate --decks /app/decks` проходить без помилок для стартової колоди `go-drills-01` з 15 Go-вправ.
3. **AC-3.** У редакторі повністю відсутні автодоповнення, підказки сигнатур і AI-доповнення. `Ctrl+S` проганяє `go test -race` і показує інлайн-діагностики або зелене проходження. На типовій картці це займає **≤ 500 мс** (медіана).
4. **AC-4.** Нескінченний цикл у коді вправи переривається приблизно через 5 с зі статусом `timeout`. Після цього `ps aux` у контейнері не показує завислих процесів.
5. **AC-5.** Ланцюжок прогресивної кати (go-05 → go-06 → go-07) проходить коректно:
   - наступний етап розблоковується лише після `pass` попереднього;
   - історія зберігається після перезапуску контейнера;
   - side-by-side diff з `solution.go` відображається правильно.
