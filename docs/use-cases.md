# DreetDojo — Use Cases

Сценарії використання MVP 1.0. Вимоги, що їх реалізують: [requirements.md](requirements.md).
Потоки виконання на рівні модулів: [hld.md](hld.md).

## Контекст

- Один користувач, одна машина. Автентифікації й багатокористувацького режиму немає.
- Одночасно існує не більше однієї **активної спроби** (attempt). Вона триває від видачі картки до `pass` або `giveup`.
- Стан активної спроби живе на сервері (таймер, лічильники, розблокування еталона), тому перезавантаження сторінки його не скидає. Перезапуск контейнера скидає активну спробу, а картка лишається в черзі.

## Актори

| Актор | Опис |
| :---- | :---- |
| **Інженер (Learner)** | Досвідчений розробник. Щодня проходить 15-хвилинні сесії, щоб відновити моторну пам'ять на синтаксис, ідіоми stdlib і роботу зі станом. |
| **Автор колод (Deck Author)** | Людина або офлайн-пайплайн генерації. Додає картки на диск і перевіряє їхню коректність, перш ніж вони потраплять у тренування. |

## UC-01. Отримати наступну картку

**Передумови:** контейнер запущено, сервер відповідає на `127.0.0.1:8787`.

**Основний потік:**
1. UI на старті перевіряє, чи є активна спроба. Якщо є, UI відновлює її (див. 1a) і далі сценарій не йде.
2. Клієнт запитує наступну картку.
3. Система синхронізує метадані карток із диска в SRS-сховище. Нові картки додаються, SRS-стан наявних не змінюється.
4. Система обирає картку в такому порядку:
   1. прострочені повторення, найдавніші першими;
   2. нові картки за `order` у колоді. Нову картку пропущено, якщо її `prereq` ще жодного разу не пройдено (`pass`), або якщо вичерпано денний ліміт нових карток.
5. Якщо була завершена спроба, система прибирає її пісочницю.
6. Система створює ізольовану робочу директорію. Туди копіюються стаб і тести, **але не еталон**.
7. Система фіксує `started_at` і обнуляє лічильники `compile_errors`, `test_fails`, `hints_used`.
8. UI показує умову, стартовий код, таймер із цільовим часом і кількість доступних підказок.

**Альтернативні потоки:**
- **1a. Відновлення після перезавантаження сторінки.** UI отримує активну спробу разом із поточним кодом із пісочниці та `started_at`. Таймер продовжує йти від `started_at`.
- **4a. Черга на сьогодні порожня.** UI показує статистику (UC-06) і пропонує *Practice Ahead*.
- **4b. Practice Ahead.** Система видає картку з найближчою майбутньою датою повторення.
- **4c. Колод немає або всі картки заблоковані.** Поводиться так само, як 4a.
- **5a. Поточна спроба ще не завершена:** 409. Пропустити картку не можна, щоб не скидати таймер і не обходити оцінку. Щоб перейти далі, треба пройти її (UC-02) або здати (UC-04). Поки спроба триває, UI не реагує на `Alt+N` і пропонує здатися.

**Постумова:** існує рівно одна активна спроба.

## UC-02. Перевірити рішення (Edit → Save → Run)

**Передумови:** є активна спроба для цієї картки.

**Основний потік:**
1. Інженер натискає `Ctrl+S`, і клієнт надсилає `card_id` та код.
2. Система атомарно перезаписує в пісочниці **лише** файл вправи (`entry_file`, за замовчуванням `kata.go`). Тести лишаються read-only.
3. Система запускає перевірку реальним тулчейном: `go test -race -json -count=1` з таймаутом.
4. Система визначає статус (`pass`, `compile_error`, `test_fail` або `timeout`) і структуровані діагностики.
5. Якщо статус не `pass`, лічильник `compile_errors` або `test_fails` збільшується на 1. UI підсвічує помилки в рядках коду й показує вивід тестів.
6. Якщо статус `pass`:
   1. таймер зупиняється, `elapsed = now − started_at`;
   2. система **об'єктивно** обчислює оцінку 1–4 з телеметрії;
   3. в одній транзакції записує спробу й оновлює розклад повторень;
   4. розблоковує еталон.
7. UI показує результат, при `pass` також оцінку й кількість днів до наступного повторення.

**Альтернативні потоки:**
- **1a. Немає активної спроби, або `card_id` не збігається з активною, або спробу вже завершено:** відмова 409, код не записується.
- **3a. Нескінченний цикл або зависання:** перевірка примусово переривається разом із усією групою процесів, статус `timeout`, збільшується `test_fails`.
- **3b. Гонка даних, яку знайшов `-race`:** статус `test_fail` з діагностикою рівня `error`.
- **2a. Код завеликий або запит некоректний:** відмова 400.

**Постумова:** при `pass` спроба завершена, стан SRS оновлено, еталон доступний. В інших випадках спроба лишається активною.

## UC-03. Отримати покрокову підказку

**Передумови:** є активна, незавершена спроба.

**Основний потік:**
1. Інженер натискає `Alt+H`.
2. Система збільшує `hints_used` і повертає наступну підказку з `meta.yaml`.
3. UI показує підказку в бічній панелі.

**Альтернативні потоки:**
- **2a. Підказки вичерпано:** 404, лічильник не змінюється.
- **2b. Немає активної спроби:** 409.

**Постумова:** кожна використана підказка знижує фінальну оцінку (див. правила оцінювання в HLD).

---

## UC-04. Здати вправу (Give Up)

**Передумови:** є активна, незавершена спроба.

**Основний потік:**
1. Інженер натискає кнопку або хоткей здачі.
2. Система закриває спробу зі статусом `giveup` та оцінкою 1 (Again).
3. Розклад скидається: `reps = 0`, `lapses += 1`, наступне повторення через 1 день.
4. Еталон розблоковується.

**Альтернативні потоки:**
- **1a. Немає активної спроби:** 409.

**Постумова:** спробу записано в історію, еталон доступний (UC-05).

---

## UC-05. Порівняти своє рішення з еталоном

**Передумови:** поточну спробу завершено (`pass` або `giveup`).

**Основний потік:**
1. Інженер натискає `Alt+D`.
2. Система перевіряє, що спробу завершено, читає поточний код із пісочниці та еталон із завантаженої колоди.
3. Система повертає обидва тексти й unified diff.
4. UI показує їх поруч (side-by-side merge view).
5. Інженер звіряє ідіоматичність свого коду й переходить далі (`Alt+N`, UC-01).

**Альтернативні потоки:**
- **2a. Спробу не завершено:** 403, еталон не видається ні в якому вигляді.
- **2b. Немає спроби для цієї картки:** 404.

## UC-06. Переглянути прогрес і слабкі зони

**Основний потік:**
1. Інженер відкриває панель статистики.
2. Система збирає дані за останні 30 днів.
3. UI показує:
   - чергу на сьогодні;
   - скільки карток пройдено сьогодні;
   - частку спроб без жодної помилки компіляції;
   - теги з найнижчою середньою оцінкою.

## UC-07. Додати та провалідувати колоду

**Передумови:** у каталозі колод є директорії карток.

**Основний потік:**
1. Автор запускає `dreet validate --decks ./decks`.
2. Система рекурсивно читає директорії карток.
3. Система перевіряє структуру:
   - обов'язкові файли на місці;
   - `meta.yaml` коректний;
   - `id` унікальні;
   - граф `prereq` посилається на наявні картки й не має циклів.
4. Для кожної картки в окремій тимчасовій директорії система перевіряє два правила:
   - стаб (`entry_file` + тести) **не проходить** перевірку (`compile_error` для формату `skeleton` теж зараховується);
   - якщо підставити еталон замість `entry_file`, тести **проходять** під `-race` без гонок і попереджень.
5. Система друкує звіт і завершується з кодом 0.

**Альтернативні потоки:**
- **5a. Хоча б одна картка невалідна:** детальний звіт по кожній битій картці, ненульовий код виходу.

**Постумова:** у тренування потрапляють лише картки, що пройшли валідацію.
