# DreetDojo — Architecture

Архітектура MVP 1.0. Вимоги: [requirements.md](requirements.md). Контракти модулів і потоки: [hld.md](hld.md).

## 1. Архітектурний стиль

**Local-first modular monolith** за принципом *Ports & Adapters*. Тонкий транспортний шар (`api` і вшитий `web`) стоїть над ізольованими доменними пакетами `deck`, `srs`, `sandbox` і `runner`. Їх зв'язує оркестратор `session`. Усе пакується в один Go-бінарник `dreet` всередині ізольованого Docker-контейнера.

## 2. Контекстна і контейнерна діаграма

```text
+--------------------------------------------------------------------+
| Host (Linux / macOS)                                               |
|                                                                    |
|  +--------------------------------------------------------------+  |
|  | Chromium --app=http://127.0.0.1:8787  (або PWA)              |  |
|  |  - Sterile CodeMirror 6 editor + @codemirror/merge (diff)    |  |
|  |  - Prompt / Timer / Hints / Diagnostics / Stats              |  |
|  +-------------------------------+------------------------------+  |
|                                  | HTTP/JSON  127.0.0.1:8787       |
|  +-------------------------------v------------------------------+  |
|  | Container "dreet"  (golang:1.26-bookworm, UID 10001, ro fs)  |  |
|  |  +--------------------------------------------------------+  |  |
|  |  | dreet (single Go binary, CGO_ENABLED=0)                |  |  |
|  |  |   [web: embed.FS + SPA]    [api: net/http]             |  |  |
|  |  |              \                 /                       |  |  |
|  |  |            +---------------------+                     |  |  |
|  |  |            | session (orchestr.) |                     |  |  |
|  |  |            +--+------+------+----+                     |  |  |
|  |  |               |      |      |                          |  |  |
```

## 3. Компоненти та напрямок залежностей

```text
cmd/dreet ──(DI-збірка)──▶ api, web, session, deck, srs, sandbox, runner
api       ──▶ session
session   ──▶ deck, srs, sandbox, runner        (лише через їхні експортовані інтерфейси)
sandbox   ──▶ deck                              (тип deck.Card)
deck, srs, runner                              — листові пакети, не імпортують інших internal/*
```

| Компонент | Відповідальність |
| :---- | :---- |
| `cmd/dreet` | CLI (`serve`, `validate`). Розбирає прапорці, збирає залежності, виконує graceful shutdown. З прапорцем `--mock` підставляє in-memory фейки трьох базових модулів. |
| `internal/api` | HTTP-хендлери, JSON DTO, мапінг доменних помилок у HTTP-коди. Бізнес-логіки тут немає. |
| `internal/web` | `//go:embed dist/*` і SPA fallback. |
| `internal/session` | Життєвий цикл активної спроби: таймер, лічильники, розблокування еталона. Тут працюють доменні правила, що зачіпають кілька модулів. |
| `internal/deck` | Читання каталогу колод (read-only), парсинг `meta.yaml`, валідація структури й графа `prereq`. |
| `internal/srs` | SQLite-сховище (`card_state`, `attempts`), чистий планувальник (`EvaluateGrade`, `ScheduleSM2`), черга, статистика. |
| `internal/sandbox` | Робочі директорії `/work/<session_id>`, безпечний запис файлу вправи, unified diff, прибирання. |
| `internal/runner` | Інтерфейс `Runner`, реєстр за `lang`, `GoRunner` поверх `go test -race -json`. |
| `internal/mock` | Фейки `runner`, `srs` і `sandbox` для `--mock`. Вони дають перевірити API і Docker від початку до кінця до появи справжніх реалізацій. |
| `web/` | Фронтенд: Vite, TypeScript і CodeMirror 6 у стерильній конфігурації. |
| `decks/` | Декларативні колоди, стартова — `go-drills-01`. |

## 4. Технологічний стек

| Шар | Технологія | Обґрунтування |
| :---- | :---- | :---- |
| Backend і HTTP | Go 1.26+, `net/http` (маршрутизація метод + шлях) | Немає зовнішніх фреймворків, споживання RAM низьке, є прямий контроль над `os/exec` і `syscall`. |
| Сховище | SQLite через `modernc.org/sqlite` | Чистий Go без CGO, один файл БД, транзакції, WAL. |
| Frontend | TypeScript + Vite + CodeMirror 6 (`@codemirror/lang-go`, `@codemirror/merge`, `@codemirror/lint`) | Легкий бандл, точний контроль над відсутністю автодоповнення, готовий side-by-side diff, вбудовування через `//go:embed`. |
| Рантайм-образ | `golang:1.26-bookworm` (Debian/glibc) | `go test -race` не працює на musl (Alpine). |
| Оркестрація | Docker Compose (`read_only`, `tmpfs`, `cap_drop`) | Відтворюваний запуск однією командою, жорстка ізоляція виконання коду, заділ під `runtime-<lang>`. |

### Сторонні Go-залежності (NFR-08)

| Залежність | Чому stdlib не вистачає |
| :---- | :---- |
| `modernc.org/sqlite` | У stdlib немає драйвера SQLite. Pure-Go варіант зберігає `CGO_ENABLED=0`. |
| YAML-парсер (`go.yaml.in/yaml/v3`) | У stdlib немає YAML, а `meta.yaml` — формат колод, зафіксований у ТЗ. |

Unified diff пишемо самі в `internal/sandbox`. Пакет diff у stdlib (`internal/diff`) не експортується, а окрема бібліотека заради однієї функції не потрібна.

## 5. Топологія розгортання

**Образ (Dockerfile, 3 стадії):**
1. `web` (`node:22-slim`): `npm ci && npm run build` збирає `dist/`.
2. `builder` (`golang:1.26-bookworm`): `dist/` копіюється в `internal/web/dist`, далі `CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" ./cmd/dreet`.
3. `runtime-go` (`golang:1.26-bookworm`):
   - створює користувача `dreet` (UID 10001);
   - прогріває `GOCACHE=/var/cache/go-build` прогоном `go test -race` по ключових пакетах stdlib;
   - копіює бінарник `dreet` і колоди.

**Контейнер (docker-compose.yml):**

| Ресурс | Налаштування |
| :---- | :---- |
| Порт | `127.0.0.1:8787:8787`, лише loopback хоста. Усередині контейнера сервер слухає `0.0.0.0:8787`. |
| `/data` | Bind-mount `./data`. Тут SQLite `dreet.db` разом із `-wal` і `-shm`. |
| `/app/decks` | Bind-mount `./decks` у режимі `ro`, тож зміни підхоплюються без перезбирання. |
| `/work` | `tmpfs`, `size=128m,mode=1777`. Робочі директорії сесій у RAM. |
| `/tmp` | `tmpfs`, `size=128m,mode=1777`, **без `noexec`**. Тут `go test` збирає й запускає тестовий бінарник (`GOTMPDIR`). |
| `GOCACHE` | Записуваний іменований том, ініціалізований з прогрітого вмісту образу (див. ADR-2). |
| Безпека | `user: 10001`, `read_only: true`, `cap_drop: [ALL]`, `security_opt: [no-new-privileges:true]`, `pids_limit: 128`, `mem_limit: 1g`, `cpus: 2.0`. |

Повністю вимкнути мережу контейнера (`--network none`) не можна, бо він сам віддає Web UI. Ізоляцію дають loopback-прив'язка, read-only rootfs, обмеження ресурсів і `GOPROXY=off`.

**Клієнт:** `chromium --app=http://127.0.0.1:8787` або PWA. Без панелей браузера `Ctrl+S` і `Alt+*` перехоплюються без конфліктів.

## 6. Розширюваність

- **Нові мови (NFR-06).**
  - Поле `lang` у `meta.yaml` обирає `Runner` з реєстру.
  - Нова мова — це одна реалізація `Runner`, наприклад `pytest --json-report` або `cargo test --message-format=json`, плюс стадія `runtime-<lang>` у Dockerfile.
  - `srs`, `sandbox`, `session`, `api` і схема БД при цьому не змінюються.
- **Альтернативні клієнти (NFR-07).** Логіка спроби живе в `session`, а не в HTTP. Тому stdio JSON-RPC (NDJSON) транспорт для плагінів VS Code / Lite XL додається як ще один адаптер поруч з `api`.
- **Інший планувальник.** `EvaluateGrade` і `ScheduleSM2` — чисті функції без БД, тож перехід на FSRS зачіпає лише `internal/srs`.

## 7. Ключові архітектурні рішення (ADR)

1. **ADR-1. Debian bookworm замість Alpine для runtime.**
   - `-race` вимагає ThreadSanitizer з glibc і CGO.
   - Сам `dreet` збирається статично (`CGO_ENABLED=0`). `gcc` з образу потрібен лише для прогону тестів вправ.
2. **ADR-2. Прогрітий `GOCACHE` і tmpfs для `/work` та `/tmp`.**
   - Без попередньої компіляції stdlib з `-race` перший прогін триває 4–6 с. Прогрів під час `docker build` і виконання в RAM скорочують цикл до 200–400 мс.
   - Go **записує** в `GOCACHE` під час кожної збірки, тому каталог кешу має бути записуваним попри `read_only: true`.
   - Рішення: іменований том Docker, змонтований у `/var/cache/go-build`. Порожній іменований том Docker при першому підключенні наповнює вмістом образу.
   - *Перевірити на AC-1/AC-3*, це ще не підтверджено прогоном.
3. **ADR-3. Оркестратор сесії окремо від HTTP-транспорту.** Життєвий цикл спроби повністю живе в `session`, тож інші транспорти додаються без дублювання логіки (NFR-07).
4. **ADR-4. Стан активної спроби на сервері.**
   - Таймер, лічильники й прапорець розблокування еталона зберігаються на бекенді.
   - Перезавантаження сторінки нічого не розсинхронізує (FR-15), а SRS-оцінка лишається чесною.
   - Активна спроба живе лише в пам'яті. У БД записуються тільки завершені спроби.
5. **ADR-5. Web UI в окремому вікні браузера замість плагіна редактора.**
   - Перший варіант, обгортка CLI над зовнішнім редактором, давав інверсний UX: людину змушували перемикатися між вікнами.
   - Плагіни (VS Code, Neovim) прив'язують до одного редактора й ускладнюють гарантію стерильності.
   - Власний CodeMirror 6 дає одне вікно й повний контроль над тим, які розширення увімкнено.
   - Плагіни лишаються як майбутні клієнти через ADR-3.
6. **ADR-6. Об'єктивна оцінка замість самооцінки.** На відміну від Anki, оцінку 1–4 обчислює ядро з телеметрії: час, помилки компіляції, падіння тестів, підказки. Так оцінку неможливо «підкрутити».
7. **ADR-7. Адаптований SM-2 замість FSRS у MVP.** Він простий, детермінований (крім jitter) і легко тестується табличними тестами. Короткий старт (1 → 3 дні) і стеля 60 днів підходять для моторної пам'яті на код. Планувальник ізольовано для подальшої заміни.
8. **ADR-8. Еталон ніколи не потрапляє в пісочницю.**
   - `solution.go` не копіюється в `/work/<session_id>`, тож ні тести, ні код користувача не можуть його прочитати.
   - Еталон видає лише `session` з пам'яті `deck` і лише після завершення спроби.
   - `dreet validate` перевіряє еталони в окремих тимчасових директоріях поза `/work`.
